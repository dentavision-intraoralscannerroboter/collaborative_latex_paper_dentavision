\subsection{Introduction}\label{ms:introduction}
To evaluate stereo-based 3D reconstruction algorithms, a large dataset of closely spaced image pairs with known relative camera poses is required.
That is difficult to obtain in practice, since jaw scans involve complex geometries and limited access paths. This section presents a simulation
environment that automatically generates such image datasets from pre-scanned dental arches of the Bits2Bites dataset \cite{bits2bites}, controlling
the relative pose between adjacent images precisely.
The environment combines an UR5e collaborative robot \cite{universalrobots_ur5e_datasheet} with a custom camera tool in PyBullet \cite{coumans2016pybullet}, using a modified IK solver for
arbitrary pose planning. High-quality images are rendered via a separate Blender instance that mirrors the simulation state, with customizable rendering settings \cite{blender_online_community}.
\subsection{Design Decisions and Implementation}\label{ms:design}
\subsubsection{Simulation with PyBullet}\label{ms:pybullet}
PyBullet \cite{coumans2016pybullet} was chosen as the physics and robot kinematics backend. This decision was made after trying to use NVIDIA URSim, which proved to be too difficult to set up in
linux due to specific driver dependencies, which weren't bundled in any easily accesible repository for fedora linux, and mujoco, which I set aside after finding a github repo\cite{ur5e_file_source} that provided a working UR5e model including mesh files and an URDF description file for the exact UR model we were targeting, which was implemeted with pybullet. It loads the UR5e robot from a URDF description, provides forward and inverse kinematics, collision detection and a GUI for inspection. All quantities are kept in SI units (metres) so that camera poses exported for the
reconstruction pipeline can be used without scaling.

\subsubsection{Robot model and camera tool}\label{ms:ik}
The modeled UR5e collaborative robot arm \cite{universalrobots_ur5e_datasheet} consists of six revolute joints, based on the afore mentioned repo\cite{ur5e_file_source}.
The custom camera tool, which is modeled after the Sirona Omnicam\cite{dentsplysirona_cerec_ac_omnicam} scanner, is mounted onto wrist\_3 of the robot. The arm parts are colored based on a gradient from green to red, which shows how far they are away from their joint limits.

The preexisting IK solver has been modified in a few ways. One of that was changing the joint limits in order to allow or disallow certain IK solutions. The elbow\_joint lower limit for example
was set to 0° to prevent ik solutions, where the forearm would bend upwards, while the wrist\_3\_joint limits were increased from 180° to the full hardware possible amount of 360° in both directions, to allow IK solutions for positions that previously resulted in unrecoverable positions. Additionally it is possible to set the seed for the IK solver to either a global seed for deterministic positioning or to the current position in order to achieve a solution close to the current one.

To reach the dense waypoint sweeps around the jaw, the inverse kinematics is used in a modified fashion. First, the damped least-squares solution (PyBullet
\code{IK_DLS}) is only a starting point: starting from a seeding joint configuration, the solver iterates up to ten times, computing the tool position
and orientation error and applying a damped Jacobian update (analytic Jacobian) until the tool pose converges onto the requested target (position
tolerance \code{1e-6} m). Second, since a single IK result may collide with the jaw, the solver is retried with different joint-space seed
configurations and the first collision-free solution is kept. Movement between waypoints is planned with the \emph{pybullet-planning} library
\cite{garrett2018pybulletplanning} (RRT-Connect with smoothing and restarts, fixed random seed for reproducible paths).

\subsubsection{Realistic rendering with Blender}\label{ms:blender}

Physics-based rendering with PyBullet's built-in renderer is not photo-realistic enough for validating stereo reconstruction algorithms. Blender
\cite{blender_online_community} was chosen as the renderer because of prior experience with the software and its Cycles path tracer, which offers
physically based materials and GPU acceleration. In practice this means that a separate Blender instance builds the scene procedurally from the same URDF data and renders
left/right stereo pairs with the Cycles engine.
\begin{figure}[!htbp]
    \centering
    \includegraphics[width=\columnwidth]{assets/manuel/blender/blender_example_together}
    \caption{A position mirrored from pybullet to blender}
    \label{fig:ms-blender_example}
\end{figure}
The scene is set up entirely by script (\code{rig.py}): The URDF link meshes are imported, re-oriented and parented to a bone armature constructed
from the joint data, and the scanner tool, both pinhole cameras and the scanner light are attached to the \code{wrist\_3} frame. Default Camera and light
parameters consist of: a full-frame 16:9 sensor (36\,{$\times$}\,20.25\,mm), a horizontal field of view of
87°, a stereo baseline of 1.7\,mm lateral offset, and near/far clipping at 1/40\,mm. The scanner light is a point light offset a few
millimeters forward from the tcp, to prevent it from clipping in the scanner stl, ensuring the same lighting for both render pairs. Rendering runs with Cycles on
the GPU (NVIDIA RTX 3060) at 1920\,{$\times$}\,1080 (16:9); the Blender render properties use 4096 samples with denoising enabled at the high and
\emph{Accurate} output quality.

So that the rendered images correspond exactly to the simulated camera poses, the simulation mirrors its state to Blender over a TCP socket
(\code{blender_link.py} on the simulator side, \code{mirror.py} in Blender, polled every 50\,ms). Each message carries the six joint angles and the
tool-center-point position; Blender applies the joint angles to the armature bones and moves both cameras and the scanner light to the mirrored TCP
position. A render request includes the target file paths for the left and right image. Blender renders both views sequentially and reports its
completion. The jaw model is loaded in both applications from the same STL files with identical transforms (world scale
\code{S} = 1 m per Blender unit). Its material is set to a roughness/specular pair of 0.8/0.2, and backface culling makes the mesh one-sided: the
inside of the dental model becomes transparent, so the underside of the jaw never appears in the rendered images.

Each currently defined scan start position in config.py moves along 21 waypoints on a parabola over one jaw side and captures 21 stereo pairs, i.e. 42 single images per scan.
Rendered at 4096 samples, one such jaw side takes roughly 2--3 hours on the RTX 3060, depending on the complexity of the visible scene. The outer side of a jaw for example takes longer than
the top side of a jaw.

\subsubsection{Generated datasets in render/}\label{ms:datasets}

Every scan is stored in its own folder under the \code{render/} directory. The folder name encodes the scan geometry: jaw type, jaw folder,
start position, render resolution and stereo baseline, e.g. \code{lower_1_a1l_1920x1080_lat1.7mm}. For each waypoint that is scanned, the folder
contains the two rendered images (\code{iL_render.png} and \code{iR_render.png}) and a pose file \code{i_pose.json}; a single
\code{render_settings.json} documents the whole scan. A render failure aborts the scan so that a folder is never left incomplete.

Each \code{i_pose.json} stores the waypoint index and label together with the left and right camera pose as position (in metres) and quaternion
(x, y, z, w) in the jaw frame. Because all quantities are kept in SI units, the reconstruction pipeline can consume these poses directly without any
scaling. The metadata of the JSON files is summarized in Table~\ref{tab:ms-dataset-settings}; Together with the measured render times (e.g.\ 9731 s
$\approx$ 2.7 h for the recorded scan above), a recorded folder is fully self-describing.

\subsection{Package/Code Structure}\label{ms:structure}

\subsubsection{Component architecture}\label{ms:architecture}

The simulation is implemented as the Python package \code{ur5e_bullet} (Figure~\ref{fig:ms-architecture}), split into a simulation core, an
interactive driver and the Blender side.

All parameters live in \code{config.py}, sorted by domain (paths, robot and kinematics, camera model, rendering, scan positions). It is
standalone-loadable (no \code{pybullet} import, no relative imports), so the Blender scripts import exactly the same configuration inside Blender's
own Python environment; it also defines the joint limits and rest poses used as IK null space and the scale factor \code{S} shared by all geometry.
\code{math_utils.py} provides pure-Python quaternion arithmetic (multiplication, conjugation) and the world-to-jaw-frame transform, and -- being free
of \code{pybullet} imports -- is likewise usable in Blender.

The simulation core is \code{sim.py}, whose \code{UR5Sim} class loads the robot URDF and the jaw STL as a collision object, implements the IK variant
(damped least squares refined by the analytic Jacobian), collision checking and RRT-Connect path planning, and executes trajectories in PyBullet.
\code{waypoints.py} generates the parabola waypoints per start position from the parameters in \code{config.py} (21 waypoints, orientation anchors
interpolated with slerp, optional \code{look_at_jaw} re-aiming). \code{camera.py} derives the left/right camera poses in the jaw frame from the
actual \code{scanner_link} transform (TCP pose in the scanner frame plus/minus the 1.7 mm lateral baseline offset) and provides the intrinsic
parameters in pixels, while \code{demo.py} writes them as \code{<n>_pose.json} together with a \code{render_settings.json} per scan.

\begin{figure*}[!t]
    \centering
    \includegraphics[width=0.95\textwidth]{assets/manuel/Architecture.pdf}
    \caption{Component architecture of the simulation environment.}
    \label{fig:ms-architecture}
\end{figure*}

The interactive control loop also lives in \code{demo.py}: a console parses the commands defined in \code{commands.py},
\code{viz.py} draws waypoint markers, look targets and cross-hairs in the PyBullet viewport, and
\code{preview_and_move} plans a collision-free path and shows it before execution. \code{blender_link.py} is the TCP client that launches the
Blender GUI instance, mirrors joint states and TCP position, forwards the render requests and waits for the completion messages.
\code{Decimate_stl.py} reduces the jaw STL to a voxel-decimated collision mesh for PyBullet.

On the Blender side, \code{rig.py} builds the whole scene procedurally (URDF meshes, armature, scanner, cameras, light, jaw import with backface
culling, Cycles settings), and \code{mirror.py} runs the socket server in Blender: it applies the received joint angles and TCP position, executes
the requested left/right Cycles renders per waypoint and reports progress. Finally, \code{visualize_scan.py} implements an additional tooling to visualize the
rendered image datasets with numpy.

\subsubsection{Getting started/Basic Commands}\label{ms:getting-started}

The project is available under the dentavision GitHub organisation \cite{ur5e_bullet_repository}. It requires Python~$\geq$~3.14, Poetry~$\geq$~2.x and
a GUI-capable Blender build available as \code{blender} on the \code{PATH}. The Poetry-managed simulation dependencies
(PyBullet, \code{pybullet-planning}, NumPy, matplotlib) are installed in the project directory with \code{poetry install}, which installs the dependencies from \code{pyproject.toml}.
After that the program can be started by running either \code{poetry run ur5e} or \code{poetry run python -m ur5e_bullet} in the project root.
On boot the arm moves to the \code{BOOT_START} pose without a jaw model loaded. The \code{>} prompt accepts the basic move and inspection commands:

\begin{itemize}[leftmargin=*]
    \item \code{m x y z [rx ry rz]} moves the TCP via RRT (asks for confirmation; orientation defaults to \code{0 0 0}). The position values should not exceed 1m in any direction due to the operational range of the robot arm (will throw an error) and the x value should be kept out of the negative range as the IK solutions tend to become somewhat unpredictable in the area behind the robot. Accepted inputs for the command would be for example \code{m 0.85 0 0.4} or \code{m 0.6 0.3 -0.4 180 90 0}.
    \item \code{o x y z} sets the tool offset. This is only useful for testing the offset value of new robot attachments instead of the current scanner model, as the correct offset of the current scanner is loaded from config.py.
    \item \code{s <speed>} sets the global move speed (default \code{0.5}). This influences the speed with which the robot arm drives aloong the rrt path of a movement.
    \item \code{@} resets the robot to the last joint configuration. This is needed, because the Pybullet GUI cant be configured to not let the mouse cursor interact with scene objects. So if clicking on the robot throws it off its position, this is for resetting that.
    \item \code{jaw <nr> [upper|lower]} loads the jaw mesh from \code{data/meshes_jaws/<nr>} into PyBullet and Blender. This can only be done, when a jaw has already been loaded by a start position.
    \item \code{q} quits the interactive loop and closes the simulation including blender.
    \item \code{start <name>} drives the robot to the start position <name> if defined in START\_POSITIONS in config.py.
\end{itemize}

\subsubsection{Defining start positions}\label{ms:start-positions}

A start position bundles a target TCP pose, the jaw placement, orientation anchors, the camera view and further parameters for a waypoint generator. The entire goal of this composition is to define a function, that creates waypoints along a parabel, which are suited to the specific side of the jaw that has to be scanned from them. The config.py in the repository\cite{ur5e_bullet_repository} already contain start positions for the first jaw, meaning waypoint parabel configurations for the outer inner and upper side of its upper and lower jaw halves.
\begin{lstlisting}[caption={start position example}, label={lst:ms-start_pos_example}, language=Python]
{
  "a1l": {
    "tcp_pos":  [0.616, 0, 0.296],
    "tcp_ori_deg": [180, 90, 0],
    "approach": [
      {"tcp_pos": [0.85, 0, 0.38],
      "tcp_ori_deg": [0, 0, 0],
      "label": "1",
      "use_current_seed": False},
      {"tcp_pos": [0.616, 0, 0.296],
      "tcp_ori_deg": [0, 90, 0],
      "label": "2",
      "use_current_seed": True}],
    "jaw_pos":  [0.65, 0, 0.3],
    "jaw_euler_deg": [0, 0, 90],
    "jaw_folder": 1,
    "jaw_type":  "lower",
    "generator":parabola_waypoints,
    "look_at_jaw": True,
    "look_target": [0.662, 0.0],
    "parabola":
      {"x0": 0.616,
      "a": 0.047,
      "z": 0.296,
      "n": 21,
      "y_max": 0.037,
      "power": 4},
    "ori_anchors":
      {"start": [90, 0, 0],
      "mid": [180, 90, 0],
      "end": [-90, 0, 0]},
    "view":
      {"apply": True,
      "distance": 0.1,
      "yaw": 90.0,
      "pitch": -89.0,
      "target": [0.65, 0.0, 0.3]},
  }
}
\end{lstlisting}
The following points describe how the configuration entries can be used to influence the waypoint generation:

\begin{itemize}[leftmargin=*]
    \item \code{tcp_pos} and \code{tcp_ori_deg}: These two values define the position and orientation the robot drives to before the jaw gets loaded. The position is supposed to be located at the origin of the parabel \ref{fig:ms-waypoint_example_front}
    \begin{figure}[H]
    \centering
    \includegraphics[width=\columnwidth]{assets/manuel/pybullet/waypoint_example_front}
    \caption{Scanner at the defined tcp\_pos and tcp\_ori\_deg of a start position}
    \label{fig:ms-waypoint_example_front}
    \end{figure}
    \item \code{approach}: Optional list of intermediate poses. These are driven to before the position from the values above. The main reason was to be able to set a default point from which the tcp\_pos is always reachable in order to prevent weird IK solutions based on the position of the robot before driving to the start position.
    \item \code{jaw_pos} / \code{jaw_euler_deg}: Placement of the jaw mesh in the PyBullet scene and Blender.
    \item \code{jaw_folder} / \code{jaw_type}: Jaw mesh directory under \code{data/meshes_jaws/} and side (\code{upper} / \code{lower}).
    \item \code{generator}: Callable that computes the waypoints from this config (e.g.\ \code{parabola_waypoints}); \code{waypoints} is a static
    list fallback when no generator is set.
    \item \code{parabola.x0}: This is the world x position of the origin of the parabel. Should equal to the x value of \code{tcp_pos}.
    \item \code{parabola.a}: This is the multiplicator of the parabel. With this its possible to stretch the height of the parabel along the world x axis.
    \item \code{parabola.z}: Corresponds to the height at which the parabel lies flat down. Should equal the z value of \code{tcp_pos}.
    \item \code{parabola.n}: Configures the amount of waypoints that are generated along the parabel. The number should be odd so the center waypoint lands on the \code{tcp_pos}.
    \item \code{parabola.y_max}: This configures the span between the two outermost waypoints, or in other words, the range between the two ends of the parabel.
    \item \code{parabola.power}: With this its possible to chose the power of the parabel. Mostly only 2 and for are needed here.
    \item \code{ori_anchors}: The point of the orientation anchors is to define 3 orientations at the origin and at each end of the parabel. the orientation of the robot at the paypoints between these anchors is interpolated with these values. The images here show the start\ref{fig:ms-waypoint_example_left} mid\ref{fig:ms-waypoint_example_front} and end\ref{fig:ms-waypoint_example_right} orientation anchor positions.
    \begin{figure}[H]
    \centering
    \includegraphics[width=\columnwidth]{assets/manuel/pybullet/waypoint_example_left}
    \caption{Scanner at W\_min with the orientation of the start anchor}
    \label{fig:ms-waypoint_example_left}
    \end{figure}
    \begin{figure}[H]
    \centering
    \includegraphics[width=\columnwidth]{assets/manuel/pybullet/waypoint_example_right}
    \caption{Scanner at W\_max with the orientation of the end anchor}
    \label{fig:ms-waypoint_example_right}
    \end{figure}
    \item \code{look_at_jaw}: This is an additional toggle that changes the orientation generation additionally to the interpolation of the orientation anchors. It changes the orientation slightly, so the view direction looks exactly at the point defined in \code{look_target}, which ensures that the gradient of the view direction lies on the same level as the parabel. This helps to create a more direct vieweing angle on the tooth surface, but is only useful for the scan of the outer side o a jaw.
    \item \code{view}: Here the Pybullet GUI camera viewpoint can be customized for a start position, so the user doesn't have to manually drag the camera there.
    \item \code{view.apply}: This is a toggle, with which the camera position change can be turned on or off.
    \item \code{view.distance}: This defines the distance of the camera from the target position.
    \item \code{view.yaw/pitch}: Yaw and pitch of the camera. Pitch can't be 90° because a pybullet bug lets the whole scenery disapper, when it has that value.
    \item \code{view.target}: the x y z position onto which the camera looks and revolves around.
\end{itemize}

The default configuration ships six positions for the three lower (\code{a1l}, \code{o1l}, \code{i1l}) and three upper arches (\code{a1u},
\code{o1u}, \code{i1u}).
\subsubsection{Start Position Commands}\label{ms:start-pos_commands}

Once a start position is active, the following additional commands can be used:
\begin{itemize}[leftmargin=*]
    \item \code{+/-}: Can be used either only as \code{+/-} to let the robot drive to the next upper/lower waypoint or as \code{+/- <n>}, which drives the robot <n> waypoints in the chosen direction.
    \item \code{scan <n>}: This allows to render a specific number <n> of waypoints, which was mostly used to test the metadata generation of the scan process.
    \item \code{scan-all <start1> [start2 ...]}: This command allows to render multiple start positions sequentially, which makes it possible to automate the hour long rendering process of multiple start positions.
\end{itemize}

The process of fully rendering a start position is visualized in Figure~\ref{fig:ms-scan-workflow}. First, a scan folder is created and the initial \code{render_settings.json} is written;
the robot then drives to the first approach pose (RRT) and sequentially moves along the waypoints to W0 without rendering. For each further waypoint it repeats the same
sequence: the robot moves to the next waypoint, the left/right camera poses are computed in the jaw frame and written to
\code{<n>_pose.json}, and a render request for the left and right image is sent to Blender. Blender renders both views via Cycles on the GPU, stores
the PNGs in the scan folder and reports completion. After the last waypoint \code{render_settings.json} is updated with the measured \code{render_duration_s}.

\subsubsection{Rendered datasets}\label{ms:results}

All six start positions were rendered into complete scan datasets. Each scan produces a folder under \code{render/} whose name encodes the scan
geometry (jaw type, jaw folder, start position, render resolution and stereo baseline), e.g.\ \code{lower_1_a1l_1920x1080_lat1.7mm}, containing
21 pose files (\code{0_pose.json} through \code{20_pose.json}), 42 rendered PNGs (left/right per waypoint) and a single \code{render_settings.json}; the
field and file layout is detailed in Section~\ref{ms:datasets}. Table~\ref{tab:ms-rendered-datasets} summarizes the six datasets together with their

The reconstruction parameter block exported by each dataset feeds the stereo pipeline directly: \code{baseline_m =
0.0034}, \code{camera_fov_deg = 87}, \code{camera_lens_mm $\approx$ 18.97}, \code{camera_far_m = 0.04}, \code{rectified = true},
\code{camera_intrinsic} with \code{fx_px = fy_px = 1011.63}, \code{cx_px = 960}, \code{cy_px = 540} on a 36\,mm $\times$ 20.25\,mm sensor. The
jaw meshes rendered by the simulation are real intra-oral scans from the Bits2Bites dataset \cite{bits2bites}, i.e.\ 200 registered pairs of upper
and lower dental arches in STL format, acquired with Carestream and 3Shape TRIOS scanners. All datasets together cover both the lower and the upper
arch from three view sides each, so that the stereo registration and model construction sections are supplied with synthetic image pairs whose
relative camera poses are known precisely.

The exported \code{pose.json} files encode the camera poses purely as position and quaternion (x, y, z, w) in the jaw frame. As a reference
implementation for how these poses are to be interpreted, \code{visualize-scan} reads the pose files and reconstructs the full camera geometry from
them: it rotates the view vector $(0,0,-1)$ by each camera's quaternion to draw the camera rays (length \code{camera_far_m}) from the left (red)
and right (blue) camera centers with \code{matplotlib}, verifies the stereo baseline by measuring $\lvert \mathbf{L}-\mathbf{R}\rvert$ (expected
constant \code{baseline\_m}) and plots the sweep order and the jaw bounding box. Any consumer of the exported data can therefore use this tool as a
reference for the pose convention before feeding the poses into the reconstruction pipeline.

\subsubsection{Reconstruction reference}\label{ms:reconstruction}

The exported stereo pairs with known intrinsics and extrinsics are the input to the subsequent image acquisition and 3D reconstruction section. The
rectified left/right pairs enable standard stereo matching (e.g.\ SGM \cite{hirschmuller_stereo_2008} or learned methods such as IGEV-Stereo
\cite{xu_iterative_2023}) followed by point triangulation with the stated baseline; the \code{camera_far_m} value bounds the penetration of the
viewing rays into the jaw surface and can be used as a near-plane limit when triangulating intra-oral geometry. All pose files together realize the
photo-granular pose ground-truth that is otherwise hard to obtain for real intra-oral scans.
